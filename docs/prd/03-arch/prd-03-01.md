# Key Architectural Requirements
In docs/prd/prd-02-01.md, we have almost refined the idea. 
Let's define application architecture before turn the idea into usable mvp.
Key architectural requirements are:
- Use MS SQL Server Database
- employ SOLID and related design principles and best practices
- App to be deployed on MS Windows IIS Server
- Use MS Dot Net 10 Blazor Server Application template
- Use Dapper as ORM for database access without embedding T/SQL in C# or middleware code and instead always using Stored Procedures to keep db level code separated. Prefix with purpose code while naming the stored procedures and other objects.
- Create UI varied complexity to display data from the database and perform basic CRUD and other operations on the data in the database
- Use MudBlazor as UI component library
- Use Development (DEV), User Acceptance Test (UAT) and Production (PROD) environments for their respective purposes with docs for preparing and deploying release in each

# Clarifications (Q&A)

| Question | Answer |
|---|---|
| Authentication mechanism? | Custom auth tables managed via Dapper + stored procedures — no ASP.NET Identity |
| Layer structure? | Layered: Presentation → Application → Domain → Infrastructure |
| Physical solution structure? | Single Visual Studio Solution with one project per layer |
| Stored procedure naming? | `sp_[Module]_[Action]` — e.g. `sp_Project_GetById`, `sp_Partner_Create` |
| DB schema management? | Code-first with manual SQL migration scripts |
| Environment topology? | One IIS server; separate IIS sub-applications for DEV, UAT, PROD; separate SQL DBs |

# Architecture PRD

## 1. Technology Stack

| Concern | Technology | Notes |
|---------|-----------|-------|
| Framework | .NET 10 Blazor Server | Server-side rendering; real-time UI via SignalR |
| UI Component Library | MudBlazor | Material Design–based Blazor components |
| Database | MS SQL Server | Relational; all schema changes via migration scripts |
| Data Access | Dapper | Lightweight ORM; all queries via stored procedures only |
| Authentication | Custom (Dapper + stored procedures) | Email/password + invitation token; no third-party identity framework |
| Hosting | MS Windows IIS | .NET 10 app hosted as an IIS application |
| IDE / Tooling | Visual Studio 2022+ | Single solution, multiple projects |

## 2. Solution Structure

```
MPSIP.sln
├── src/
│   ├── MPSIP.Web/               # Presentation — Blazor Server app (Pages, Components, Layouts)
│   ├── MPSIP.Application/       # Application — use cases, services, interfaces, DTOs
│   ├── MPSIP.Domain/            # Domain — entities, value objects, domain rules
│   └── MPSIP.Infrastructure/    # Infrastructure — Dapper repositories, DB connection, email sender
├── docs/                        # PRDs and documentation
└── publish/                     # Release artifacts
```

### Project Dependency Rules (enforced at compile time)

```
MPSIP.Web          → MPSIP.Application
MPSIP.Application  → MPSIP.Domain
MPSIP.Infrastructure → MPSIP.Application, MPSIP.Domain
```

> `MPSIP.Web` **never** references `MPSIP.Infrastructure` directly. Infrastructure is registered into the DI container via an extension method called from `Program.cs`.

## 3. Design Principles

| Principle | Application |
|-----------|------------|
| **Single Responsibility** | Each class/service handles one concern; Blazor components contain no business logic |
| **Open/Closed** | Extend via interfaces; avoid modifying concrete implementations |
| **Liskov Substitution** | Repository interfaces defined in Application; concrete Dapper implementations in Infrastructure are interchangeable |
| **Interface Segregation** | Narrow, focused interfaces per module — e.g. `IProjectRepository`, `IPartnerRepository`, `IContributionRepository` |
| **Dependency Inversion** | All dependencies injected via constructor; no `new` on concrete service classes outside the composition root |
| **DRY** | Shared logic in Application services; no duplicated stored procedure calls across layers |
| **Separation of Concerns** | T-SQL lives only in stored procedures; no business logic in SQL; no inline SQL in C# |

## 4. Data Access Pattern

### Rule
> All database interaction must go through **stored procedures only**. Inline T-SQL or parameterised query strings are not permitted in C# code at any layer.

### Database Object Naming Convention

| Object Type | Pattern | Example |
|-------------|---------|---------|
| Stored Procedure | `sp_[Module]_[Action]` | `sp_Project_GetById`, `sp_Partner_Create`, `sp_Contribution_ListByProject` |
| Table | `[Module]` (PascalCase) | `Project`, `Partner`, `Contribution`, `Distribution` |
| View | `vw_[Module]_[Description]` | `vw_Project_Summary`, `vw_Partner_Stakes` |
| Scalar Function | `fn_[Module]_[Description]` | `fn_Distribution_CalcShare` |
| Index | `ix_[Table]_[Columns]` | `ix_Partner_ProjectId` |
| Primary Key | `pk_[Table]` | `pk_Project` |
| Foreign Key | `fk_[Table]_[RefTable]` | `fk_Partner_Project` |

### Repository Pattern

```
// Application Layer — interface
public interface IProjectRepository
{
    Task<ProjectDto?> GetByIdAsync(int id);
    Task<int> CreateAsync(CreateProjectCommand cmd);
    Task<IEnumerable<ProjectSummaryDto>> ListByOwnerAsync(int ownerId);
    // ...
}

// Infrastructure Layer — Dapper implementation
public class ProjectRepository : IProjectRepository
{
    // Calls sp_Project_GetById, sp_Project_Create, sp_Project_ListByOwner, etc.
}
```

## 5. Authentication Architecture

Custom lightweight auth — no ASP.NET Identity:

| Component | Details |
|-----------|---------|
| **AppUser table** | `Id`, `Email`, `PasswordHash`, `Salt`, `IsActive`, `CreatedAt`, `OwnerId` |
| **Session** | Blazor Server `AuthenticationStateProvider`; session cookie (server-side) |
| **Password hashing** | BCrypt (`BCrypt.Net-Next` NuGet package) |
| **Invitation tokens** | `InvitationToken` table — `Token` (GUID), `ProjectId`, `Email`, `ExpiresAt`, `UsedAt`; 48h TTL |
| **Stored procedures** | `sp_Auth_GetUserByEmail`, `sp_Auth_CreateUser`, `sp_Auth_CreateInvitation`, `sp_Auth_RedeemInvitation` |
| **Role-based access** | Claims populated at login from user's project roles; `AuthorizeView` in Blazor |

---

## 6. Database Schema Management

- All schema changes delivered as **sequential numbered SQL migration scripts**
- Naming convention: `V{###}__{Description}.sql` — e.g. `V001__CreateAppUser.sql`, `V002__CreateProject.sql`
- Scripts stored under: `src/MPSIP.Infrastructure/Database/Migrations/`
- Stored procedures stored under: `src/MPSIP.Infrastructure/Database/StoredProcedures/[Module]/`
- A `SchemaVersion` table records each applied migration (number, description, applied timestamp)
- Migrations run in order; re-running a previously applied migration is a no-op

## 7. Environment Strategy

| Environment | Purpose | IIS Path | SQL Database |
|-------------|---------|----------|-------------|
| **DEV** | Active development and integration | `/dev` | `MPSIP_DEV` |
| **UAT** | Owner/partner acceptance testing | `/uat` | `MPSIP_UAT` |
| **PROD** | Live system | `/` (root) | `MPSIP_PROD` |

- Each environment uses its own `appsettings.{Environment}.json`
- Connection strings and credentials stored in **Windows environment variables** — never in source control
- Deployment runbooks for each environment documented separately under `docs/prd/03-arch/`

## 8. UI Architecture (Blazor Server + MudBlazor)

```
MPSIP.Web/
├── Pages/
│   ├── Auth/            # Login, Register, AcceptInvitation
│   ├── Dashboard/       # Owner dashboard, Partner dashboard
│   ├── Projects/        # List, Detail, Create, Edit
│   ├── Partners/        # Invite, Manage, Stake definition
│   ├── Contributions/   # Log and view contributions
│   ├── Distributions/   # Declare and view distributions
│   └── Admin/           # User and system management (owner only)
├── Components/          # Reusable non-routable Blazor components
├── Layouts/             # MainLayout, AuthLayout
├── Services/            # Scoped UI services (auth state, navigation helpers)
└── wwwroot/             # Static assets (CSS, JS, images)
```

- `MudThemeProvider`, `MudDialogProvider`, `MudSnackbarProvider` declared in root layout
- Pages and components gated by `<AuthorizeView>` with policy-based role checks
- Blazor components call **Application layer services only** — no direct repository or DB calls

---

## 9. Cross-Cutting Architecture Decisions

| Concern | Decision |
|---------|---------|
| **Multi-tenancy readiness** | All domain tables include `OwnerId` column from day one; single-owner MVP uses a fixed owner record |
| **Audit trail** | `CreatedAt`, `CreatedBy`, `ModifiedAt`, `ModifiedBy` on all major tables; populated via stored procedures |
| **Soft delete** | `IsDeleted` flag on all major entities; no hard deletes in production |
| **Error handling** | Global Blazor error boundary; structured logging via `Microsoft.Extensions.Logging`; errors surfaced via MudBlazor Snackbar |
| **Configuration** | `IOptions<T>` pattern; no magic strings; environment-specific `appsettings.{env}.json` |
| **DI registration** | All services registered in `Program.cs`; Infrastructure services registered via `AddInfrastructure()` extension method |
