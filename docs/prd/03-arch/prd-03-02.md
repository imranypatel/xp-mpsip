# Prototype PRD

## 1. Definition

The MPSIP MVP prototype is a **fully working Blazor Server web application** covering all 9 feature areas defined in `prd-02-01.md`. It is built on the architecture established in `prd-03-01.md` — real SQL Server, Dapper, stored procedures, four-layer solution — and is presentable to stakeholders.

This prototype **is** the MVP; it is not a throwaway. It will be iteratively hardened into the production system.

---

## 2. Feature Scope

All 9 MVP feature areas must be functional end-to-end in the prototype:

| # | Feature Area | Prototype Deliverable |
|---|---|---|
| 1 | **Authentication & Onboarding** | Login, Register, Accept Invitation pages; session-based auth with role claims |
| 2 | **Project Management** | Create/edit/view Manufacturing project; apply starter template; lifecycle status display |
| 3 | **Partner & Stake Management** | Invite partner by email; assign roles; define percentage stakes; digital acknowledgement (checkbox + e-signature) |
| 4 | **Contribution Tracking** | Log contribution (Man / Material / Money) by owner or partner; contribution list per project |
| 5 | **Incentive & Distribution** | Declare distribution event; calculated share per partner; recipient acknowledgement |
| 6 | **Workflow & Task Management** | Task list seeded from Manufacturing template; status update workflow; resource assignment |
| 7 | **Dashboard & Reporting** | Owner dashboard (project cards + key metrics); Partner dashboard; per-project detail view |
| 8 | **Alerts & Notifications (In-App)** | Notification bell + list; notifications triggered on: invitation sent, contribution due, milestone approaching, distribution declared |
| 9 | **Project Closure** | Owner-triggered closure workflow; final distribution step; partner feedback form; project archive |

## 3. Solution Scaffold

### Structure
```
MPSIP.sln
└── src/
    ├── MPSIP.Web/               # .NET 10 Blazor Server (entry point)
    ├── MPSIP.Application/       # Services, interfaces, DTOs, commands
    ├── MPSIP.Domain/            # Entities, value objects, enums
    └── MPSIP.Infrastructure/    # Dapper repositories, DB, email
```

### Key Configuration Files
- `appsettings.json` — shared defaults
- `appsettings.Development.json` — DEV connection string + env label
- `appsettings.UAT.json` — UAT connection string
- `appsettings.Production.json` — PROD connection string
- Credentials: Windows environment variables only — never in source control

## 4. Database

### Schema Migration Scripts
Location: `src/MPSIP.Infrastructure/Database/Migrations/`

| Script | Content |
|--------|---------|
| `V001__CreateSchemaVersion.sql` | `SchemaVersion` tracking table |
| `V002__CreateAppUser.sql` | `AppUser`, `InvitationToken` tables |
| `V003__CreateOpportunityKind.sql` | `OpportunityKind` lookup |
| `V004__CreateProjectTemplate.sql` | `ProjectTemplate`, `TemplatePhase`, `TemplateTask` tables |
| `V005__CreateProject.sql` | `Project`, `ProjectPhase`, `ProjectTask` tables |
| `V006__CreatePartner.sql` | `Partner`, `PartnerRole`, `PartnerAgreement` tables |
| `V007__CreateContribution.sql` | `Contribution` table |
| `V008__CreateDistribution.sql` | `DistributionEvent`, `DistributionShare` tables |
| `V009__CreateNotification.sql` | `Notification` table |
| `V010__CreateProjectClosure.sql` | `ProjectClosure`, `PartnerFeedback` tables |

### Seed Scripts
Location: `src/MPSIP.Infrastructure/Database/Seeds/`

| Script | Content |
|--------|---------|
| `Seed_OpportunityKinds.sql` | Manufacturing, Trading, Servicing lookup rows |
| `Seed_ManufacturingTemplate.sql` | Manufacturing starter template (7 phases + default tasks) |
| `Seed_DevData.sql` | DEV-only: owner account, 2 partners, 1 demo project, contributions, distributions |

### Stored Procedures
Location: `src/MPSIP.Infrastructure/Database/StoredProcedures/[Module]/`

One SP file per action; naming: `sp_[Module]_[Action].sql`. Created for every repository method.

## 5. Build Phases (Implementation Order)

| Phase | Label | Content |
|-------|-------|---------|
| **P1** | Scaffold | Create VS solution + 4 projects; wire DI; configure MudBlazor; `appsettings` per env; base layouts |
| **P2** | Database | Run all migration scripts; create all stored procedures; run seed scripts |
| **P3** | Auth | `AppUser` + `InvitationToken` repos + SPs; custom `AuthenticationStateProvider`; Login / Register / AcceptInvitation pages |
| **P4** | Core Domain | Domain entities; Application interfaces; Infrastructure Dapper repos for: Project, Partner, Template |
| **P5** | Features | Blazor pages + Application services for features 2–9 (in dependency order: Project → Partner → Contribution → Distribution → Workflow → Dashboard → Notifications → Closure) |
| **P6** | Notifications | In-app notification service; bell component; trigger hooks in other feature services |
| **P7** | Polish | MudBlazor theme + palette; consistent navigation; responsive spot-checks; remove all placeholder text; seed data entry walkthrough |
| **P8** | Deploy | `dotnet publish` per environment; deploy to IIS DEV/UAT/PROD sub-apps; smoke test each |

---

## 6. UI Standards for Prototype

- **Theme**: MudBlazor `MudThemeProvider` with a consistent primary/secondary palette
- **Layout**: `MainLayout` (sidebar nav + top bar + notification bell); `AuthLayout` (centred card)
- **Navigation**: Sidebar links: Dashboard · Projects · My Contributions · Distributions · Notifications
- **Error handling**: MudBlazor `MudSnackbar` for user-facing errors; global `ErrorBoundary` in Blazor
- **Loading states**: `MudProgressLinear` or `MudSkeleton` during data fetches
- **No placeholder text**: all labels, headings, and help text must be real content

---

## 8. Acceptance Criteria for Prototype

The prototype is complete when:

- [ ] All 9 feature areas are functional end-to-end in DEV
- [ ] Owner can log in, create a Manufacturing project, invite a partner, and view the dashboard
- [ ] Partner can accept invitation, log a contribution, and acknowledge a distribution
- [ ] Notifications appear in-app for key trigger events
- [ ] Project can be closed with feedback captured
- [ ] DEV, UAT, and PROD environments are deployed and accessible via IIS
- [ ] Seed data is present in DEV; UAT and PROD start with lookup data only
- [ ] No inline SQL in C# at any layer; all DB access via stored procedures
- [ ] UI is presentable to stakeholders — consistent MudBlazor theme, no placeholder text
